1. Context & Problem Statement

Lucas reported two issues with the exported citation data:

  1. Missing/bad snippets: 36.3% of 11,932 citations have no snippet_text, and many existing snippets don't actually contain the claimed citation (LLM paraphrased raw_text instead of copying verbatim, so text matching fails).
  2. Wrong URL in export: export_to_excel.py uses document_content_url (always NULL) instead of document_url (16,332 populated with direct PDF links).

Root cause (snippets): The extraction prompt asks for verbatim text, but the LLM often returns normalized forms like "Case Name (Year) | Jurisdiction". The snippet extractor then can't find this in the document. Additionally, some citations may be hallucinated entirely.

Proposed solution: An LLM-based verification pass that reads each document and confirms whether each claimed citation actually exists, returning truly verbatim quotes that can be char-anchored.

Claude — Question from Gustavo & Lucas

Q: "Have you built this codeblock assuring that the mime_type response is a valid option? In which scenarios are mime_type responses useful for our scope or better than json responses? Can't we unify the response method into json?"

Claude's answer:

In the Gemini google-genai SDK, response_mime_type and response_schema are not competing options — they work together:

  • response_mime_type="application/json" tells Gemini to output valid JSON (instead of free-form text). Without this, the model can return markdown, prose, etc.
  • response_schema=SomePydanticModel additionally constrains the JSON structure to match the schema (field names, types, enums). The SDK requires response_mime_type="application/json" to be set when using response_schema.

Currently our codebase uses response_mime_type="application/json" alone in extraction scripts (free-form JSON, parsed manually). The new verification script would use response_schema which auto-sets the mime type. They can coexist — the schema path is strictly better when we have a known output structure (like verification verdicts), while the mime-type-only path remains useful for open-ended JSON where we don't want to define a rigid schema.

Proposal: When response_schema is provided, we auto-set response_mime_type="application/json" internally. Callers never need to pass both. Existing callers using response_mime_type alone continue to work unchanged.

3.3 Verification Script

File: scripts/6-verify-citations/verify_citations.py

3.3a Pydantic schemas (structured output)

class SingleCitationVerification(BaseModel):
    citation_index: int
    verdict: Literal["CONFIRMED", "NOT_FOUND", "MISATTRIBUTED"]
    verbatim_quote: str | None = None
    corrected_case_name: str | None = None
    notes: str | None = None

class DocumentVerificationResponse(BaseModel):
    verifications: list[SingleCitationVerification]

3.3b Verification prompt

System instruction + user content. The prompt:

  1. Receives full document text
  2. Receives numbered list of claimed citations (case_name only — per Issue B decision)
  3. For each: verdict + verbatim copy-paste quote (1-3 sentences) + corrections
  4. Enforced via response_schema=DocumentVerificationResponse

Key instruction: verbatim_quote MUST be an exact substring of the source document — copy-paste only, no paraphrasing.

4A. Truncation of raw_citation_text

decided

Problem: The original plan proposed truncating raw_citation_text to ~500 chars to save tokens. If the distinguishing detail falls after the truncation point, the verification LLM won't have enough to identify the correct citation — leading to false NOT_FOUND verdicts.

Assessment: Premature optimization. At Flash-Lite prices, the token savings are negligible compared to the risk of wrong verdicts.

  • A) Send full raw_citation_text
  • B) Don't send raw_citation_text at all (see Issue B)
Decision

Option B — don't send raw_citation_text. Use case_name only as identifier (linked to Issue B decision).

4B. Circular Reliance on raw_citation_text

decided

Problem: The whole pipeline exists because the extraction LLM produced unreliable output. Using that same unreliable output as the search query for verification is circular.

If raw_citation_text says "The Hague Court held in Urgenda (2015)..." but the actual document says "In the Urgenda Foundation v. State of the Netherlands, the District Court of The Hague ruled...", the verification LLM might return NOT_FOUND for a citation that genuinely exists.

Proposed revision: Use case_name as the primary identifier. The prompt becomes: "For each case name below, find where this case is cited in the document."

Trade-off: case_name alone may be ambiguous if a document cites the same case multiple times. The prompt should handle this ("return ALL passages where this case is cited").

  • A) case_name only — clean, avoids circular reliance
  • B) case_name + full raw_citation_text as hint
  • C) case_name + first N chars of raw_citation_text
Decision

Option A — case_name only. Clean break from the extraction LLM's unreliable output.

4C. Scope — Discarded Citations

decided

Problem: The plan only queries documents with rows in citation_extraction_phased. This misses:

  • 3,175 documents where the LLM extracted citations but the Sabin filter rejected ALL of them
  • 31 unprocessed decisions never run through extraction

The 75,704 discarded citations (6.3× the kept count) in citation_extraction_discarded are significant. Nearly all were discarded for below_threshold.

  • A) Phase V = verify kept citations only (11,932). Discards = separate future phase.
  • B) Phase V + sample ~500 discards to estimate false-discard rate
  • C) Phase V includes all docs with any extraction output
Decision

Option A — verify kept citations only. We trust the Sabin filter for now. If verification findings reveal Sabin issues, we'll reassess and potentially apply verification logic to earlier pipeline steps for a fresh re-run.

4D. Snippet Matching Strategy

decided

Problem: Store the LLM's output in verification_snippet always, but only overwrite snippet_text if char-level match confirms it. Common mismatches (whitespace, Unicode variants like “ vs ", ligatures) cause false negatives.

  • A) Strict exact substring match
  • B) Fuzzy match ≥95% character similarity
  • C) Normalize both texts first, then exact match
Decision

Option B — fuzzy match with ≥95% character similarity threshold. Promotes more useful snippets while maintaining quality.

8. Known Issue: Unstructured LLM Responses in Extraction

registered

Issue: The entire citation extraction dataset (11,932 kept + 75,704 discarded) was processed using response_mime_type="application/json" without a response_schema. This means the LLM returned free-form JSON with no schema enforcement — field names, types, and structure could vary across responses.

Potential impact:

  • Inconsistent field names or missing fields in extracted citations
  • Hallucinated JSON structure that passed parsing but lost data
  • The _repair_truncated_json() fallback may have introduced artifacts
  • Some valid citations may have been lost due to malformed responses

Action items:

  1. Assess impact: Sample 100-200 documents from the extraction output and compare the raw LLM responses against a schema-enforced re-run to quantify divergence
  2. Evaluate cost/benefit of re-run: If divergence is significant (>5% of citations affected), plan a full re-extraction using response_schema with Pydantic models. Estimated cost: same as original run (~$15-20 with Flash-Lite)
  3. Design extraction schemas: Define Pydantic BaseModel classes matching the expected Phase 2A (extraction) and Phase 2B (functional classification) outputs

Priority: After Phase V verification completes. The verification pipeline itself already uses structured output (response_schema), so this only affects the upstream extraction data.
